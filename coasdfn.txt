The mapping is generated, not written

docs/template-contract.md closed by naming what it had not done: the 433-field mapping table.
It is now docs/template-tags.json, produced from the .docx bytes by

  npm run templates:tags

The extractor rejoins tags split across XML runs — Word routinely stores {listSAll} as
"{listS" + "All}" — and then walks each template's section stack to record WHICH PAYLOAD ROOT
every field is read from. That last part is the whole game. A field placed under the wrong
root renders blank with no error, and that is exactly what defect 1 is: temp06 asks for
{#budget}{listSAll} and the old render passed Fbudget but not budget, so the approved amount
has printed blank on every กนศ.06 ever produced. A mapping guessed from field names would have
reproduced the bug faithfully.

The arity limits are read from that same generated file rather than typed in, so replacing a
template and re-running the extraction moves them with it.

One defect I could NOT fix, and did not paper over

temp04 contains TWO full 15×12 month grids over the same startM/endM values. 180 cells test
"startM_n <= m && endM_n >= m" — correct. 176 cells test the same months with "||" — which
shades every column from the first month the bar touches to the end of the year. Wrong for any
activity shorter than a full year.

It cannot be fixed from the payload (both grids read the same two numbers) and the templates
are fixed inputs that README.md says not to edit. So: the assembler supplies correct integer
month indices, the && grid is right, the || grid over-shades exactly as it does today, and the
whole thing is quantified in docs/template-contract.md open item 2. FIXING IT MEANS EDITING
temp04.docx, WHICH IS YOUR CALL.
